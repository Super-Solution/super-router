# SuperRouter 產品需求文件（PRD）

- 文件版本：0.1
- 更新日期：2026-11-04
- 狀態：產品草案，供後續技術設計與實作拆解；不代表功能已實作。
- 產品定位：Ultimate AI routing, charging and serving platform。
- 文件範圍：產品需求。配套設計見 [技術架構](ARCHITECTURE.md)、[資料模型](DATA_MODEL.md)、[API 規格](API_SPEC.md) 與 [實作計畫](IMPLEMENTATION_PLAN.md)；skill 與範例 App 尚待實作。

## 1. 產品願景

SuperRouter 是可作為套件整合、可自行部署，也可使用託管 Cloud 的 AI 服務基礎設施。開發者透過一致的介面提供 AI 服務，設定模型供應、routing、售價、訂閱及額度，不必為每個產品重建模型轉發與計費系統。

產品的基本單位是 **Service**：開發者對使用者承諾的一項 AI 能力。Service 可以綁定指定模型、明確模型集合，或具有任務意義的 tier，並搭配獨立的收費規則。供應商或模型的調整不應迫使客戶更換 Service 介面。

核心價值：

1. 統一各家模型的呼叫、用量記錄與成本核算。
2. 讓開發者以 token、任務、訂閱及 credits 組合販售 AI 能力。
3. 在能力、資料處理限制與預算內，依成本、穩定性、延遲及品質選擇供應來源。
4. 同時提供平台供應的 Cloud 與允許 BYOK 的 self-host，沿用一致的核心概念。
5. 後續允許使用者將自己的 SuperRouter 額度授權給應用程式，形成跨應用程式的使用體驗。

## 2. 決策狀態與產品邊界

### 2.1 使用者已提出的方向

| 項目 | 要求 |
| --- | --- |
| 模型供應 | 支援多 Provider 轉發，記錄 token 與對應計價 |
| 商業模式 | 支援 per-task、subscription、per-token、credits |
| Routing | 允許開發者設定成本、穩定、合規等政策，提供價格、成本、Health、Log 工具 |
| 部署 | 同時有 Cloud 與 self-host；上游 BYOK 僅供 self-host |
| Cloud 額度 | 使用者或開發者可向 SuperRouter 購買模型使用額度 |
| 模型選擇 | 同時有 specific model 與 high／low 等模糊 tier |
| 交付形態 | 類似套件的產品，後續補上 skill 與範例 App |

### 2.2 本 PRD 採用的建議預設

以下用於建立可實作的基線，仍可在技術設計前調整：Service 作為販售單位；先過硬限制再做 routing 評分；供應成本與客戶收費分帳；第一版以文字推論與 Developer pays 為主；不同 workspace 的 credits 不自動互通；第一版每個帳戶單一結算幣別，不做外匯轉換。

套件的語言、生態、授權條款、正式價格、付款服務商與部署規模尚未決定。本文件不預設開源授權，也不預設必須採用微服務。

## 3. 使用者與主要情境

| 角色 | 主要需求 | 成功結果 |
| --- | --- | --- |
| AI App 開發者 | 用同一介面接入模型，提供套餐與額度 | 能將 AI 能力接入自己的 App，查到每筆用量與毛利 |
| 自架服務營運者 | 使用自有 Provider keys，控制資料與政策 | 能自主維運與設定路由，不必依賴 Cloud 完成核心請求 |
| 團隊管理員／財務 | 管理成員、預算、價格與對帳 | 支出有上限，帳目可追溯並可匯出 |
| 終端使用者 | 知道可使用哪些能力，以及花費多少 | 額度、訂閱與扣款透明，錯誤不造成重複扣款 |
| SuperRouter 平台營運者 | 管理 Cloud 供應、售價與服務品質 | 能隔離 Provider 故障，追蹤成本與供應健康 |

主要旅程：

1. **Cloud 開發者**：建立 workspace → 購入平台額度 → 建立 Service 與售價 → 選模型或 tier → 設定預算 → 取得 API key → App 呼叫 → 查詢用量、成本與客戶扣款。
2. **Self-host 開發者**：安裝套件／部署服務 → 接入自有 Provider credentials → 建立相同 Service 與計費設定 → App 呼叫 → 在本地管理與對帳。
3. **訂閱使用者**：取得方案 → 每期獲得 entitlement 與額度 → 消耗服務 → 額度不足時停止或依事前同意超額計費。
4. **個人錢包使用者，後續階段**：登入 SuperRouter → 授權 App 使用指定 Service 與預算 → 使用 → 檢視花費或撤銷授權。

## 4. 交付形態與部署矩陣

核心必須能以套件方式整合，不把管理後台當成唯一入口。Standalone server、Cloud、SDK、skill 與範例 App 都應使用同一套已定義的核心行為。

| 能力 | Cloud | Self-host |
| --- | --- | --- |
| 平台供應的模型與額度 | 必須 | 後續可選接入 |
| 自備上游 Provider key | 禁止 | 必須 |
| Service、模型群組、routing、計價 | 必須 | 必須 |
| 本地核心推論、用量與帳務 | 由平台營運 | 不依賴 Cloud 帳號或授權回呼完成 |
| Provider secrets 與資料管理 | 平台負責 | 部署者負責 |
| 收取開發者客戶的款項 | 透過獨立付款整合 | 透過部署者的付款整合 |
| 跨 App 使用者錢包授權 | 後續階段 | 聯邦／跨部署授權不在初期範圍 |

Cloud 禁止 BYOK 必須由後端與供應來源政策強制執行，不能只隱藏 UI。Cloud 的 SuperRouter API key 是平台呼叫憑證，不屬於上游 BYOK。

預期 repository 交付分區如下；目前 P1 核心與最小範例已可本地執行，實際驗證與未完成項目見 [P1 驗證紀錄](P1_VALIDATION.md)：

| 建議路徑 | 後續用途 |
| --- | --- |
| `packages/` | 核心引擎、Provider adapters、SDK 與必要的整合套件；實際拆分由架構文件決定 |
| `apps/` | Standalone server 與管理介面 |
| `examples/` | 可執行的最小串接、計價及 self-host 範例 |
| `skills/` | 協助 coding agent 安裝、設定、串接及診斷的 skill |
| `docs/` | PRD、架構、資料模型、API、操作與實作計畫 |

## 5. 核心領域概念

本節是產品資料概念與關係，不是資料表或 migration 規格。

| 概念 | 責任與關係 |
| --- | --- |
| Workspace | 開發者／營運者的租戶邊界，擁有 Service、專案、政策與帳務 |
| Project / Environment | 區分應用與測試／正式設定，API key 必須綁定可用範圍 |
| Member / Role | 定義管理、開發、財務及唯讀存取權限 |
| Customer | 開發者產品中的付款或使用主體；外部 customer ID 必須限定於 workspace |
| Provider / Connection | 供應商及實際連線，包含地區、能力、credentials 引用與健康狀態 |
| Model / Offering | 模型身分與某供應來源提供的版本、能力、價格及限制；同模型可有多個 offering |
| Model group / Tier | 明確候選集合或如 `coding/high` 的能力別名 |
| Routing policy | 硬限制、評分偏好、fallback、重試與預算規則的版本化集合 |
| Service / Service version | 對外能力契約，綁定輸入／輸出、模型選擇、routing 與計價版本 |
| Price book / Price version | 對客戶的價格與生效時間；與 Provider 成本價目分離 |
| Plan / Subscription / Entitlement | 方案、訂閱狀態及其授予的使用權／週期額度 |
| Billing account / Credit bucket | 貨幣或 credits 的帳戶與額度批次，區分購買、訂閱、贈送及到期規則 |
| Reservation / Ledger entry | 預留額度與不可覆寫的扣款、釋放、退款、調整紀錄 |
| Request / Attempt / Usage record | 一次客戶請求、其多次上游嘗試及可稽核的用量證據 |
| Task / Task run | 後續階段的任務契約與執行實例，可包含多次 Request |
| Authorization grant | 後續使用者錢包授權，限定 App、Service、預算與期限 |
| Audit event / Health sample | 設定變更紀錄與供應健康觀測 |

關係原則：一個 Service 可有多個版本；一個 Request 固定使用一組已解析的設定版本，並包含一個或多個 Attempt。每個 Attempt 的成本獨立記錄，客戶收費則由 Request 或 Task 的商業契約決定。每筆扣款必須追溯到付款方、使用量、價目版本與原始請求。

## 6. 功能需求

### FR-01：模型轉發與 Serving

- 提供一致的文字推論介面及串流回應，保留 request ID 與實際模型資訊。
- Provider adapters 必須明確宣告支援能力；不支援的參數應在呼叫前拒絕，不可默默忽略。
- tool calling 與結構化輸出只在候選 offering 宣告支援時接受；第一版不代替 App 執行外部工具副作用。
- 記錄 input、output、cached 等可取得的用量；保留原始 Provider usage 與正規化結果，避免重複計算。
- 支援逾時、取消、限流、串流中斷與 Provider 錯誤的可識別狀態。
- Provider 未回傳完整用量時，標記估算或待對帳，不可當成零成本或偽裝成確定值。

驗收：同一 Service 能使用至少兩個不同 Provider adapter 完成文字與串流請求；不相容能力在執行前被排除；每次成功或失敗的 Attempt 都可查詢。

### FR-02：Service 與版本

- 開發者可建立、測試、發布、停用 Service；草稿不可被正式客戶呼叫。
- Service 定義能力、模型選擇、routing、計費、配額與存取範圍。
- 發布後的版本與價目不可原地覆寫歷史；新版本影響後續請求，進行中的請求沿用已固定版本。
- 明確展示輸入限制、輸出能力、收費單位及失敗／取消收費規則。

驗收：修改模型與售價後，舊請求仍能重建原本的路由設定與扣款依據。

### FR-03：Specific、Pool 與 Tier

- Specific：固定模型身分；允許在同模型的相容 offering 間選路，不得偷偷更換模型。
- Pool：開發者列出允許的候選模型與版本。
- Tier：以任務命名，例如 `chat/low`、`coding/high`；定義能力門檻、候選集合、價格上限與路由政策。
- 預設禁止跨 tier 降級；如開發者開啟，須定義可降級範圍並在回應與 Log 呈現。
- 模型集合變更必須版本化；自動採用新候選模型屬於可選政策，不得默認影響固定版本客戶。

驗收：查詢與實際請求均可看到選到的模型和 tier 版本；無符合候選時回傳明確原因，不越過限制。

### FR-04：Routing policy

路由順序：存取與額度檢查 → 能力／合規硬限制 → 健康與容量檢查 → 預算可行性 → 偏好評分 → 執行與受限 fallback。

| 類型 | 可設定條件 |
| --- | --- |
| 硬限制 | Provider allowlist／denylist、地區、資料處理標籤、能力、context 長度、單次預算、價格上限 |
| 偏好 | 預估成本、延遲、近期成功率、任務品質評估、Provider 偏好 |
| 執行限制 | timeout、重試次數、最大總嘗試次數、fallback 清單、是否跨 tier |

- 提供成本優先、低延遲、穩定優先、品質優先與自訂權重；不同量綱須正規化，不能直接相加。
- 自訂權重只作用於已符合硬限制的候選；合規要求不能被價格抵銷。
- 品質評分需有來源、適用任務與更新時間；第一版可使用開發者提供的評級，不宣稱有通用智能品質判定。
- 健康指標依 offering 與區域觀察，區分未知、正常、劣化與不可用；使用觀測窗口與最低樣本規則，避免單次錯誤直接代表全面失效。
- 供應故障可觸發暫停選用與恢復探測；低樣本／無樣本時採明確預設，而不是當成滿分。
- 提供 policy dry-run，展示候選排除原因、評分依據與估計價格，不實際呼叫付費模型。
- 對資料處理／合規標籤記錄來源、驗證狀態與期限；標籤本身不構成平台對外的法規認證。

驗收：便宜但不符地區限制的 offering 永遠不被選用；fallback 也須通過相同硬限制與剩餘預算；路由結果可解釋。

### FR-05：成本、用量與銷售計價

必須區分 Provider cost、Usage、Customer billing 與 Entitlement，不以單一餘額欄位代替完整帳務。

| 方式 | 行為 |
| --- | --- |
| Per token | 依固定價目版本與實際 token 類型收費；cached token 的包含／扣除關係需依 adapter 明確轉換 |
| Per task | 依任務契約的成功條件收費；一個任務可包含多次模型呼叫，失敗規則需事前明示 |
| Subscription | 週期性提供權限與額度；可限定 Service、tier、用量、併發與期限 |
| Credits | 用開發者定義的單位支付服務，可與 token 或 task 價目組合 |

- Credits 不是 token、法幣或 Provider 成本的同義詞。每個 credits 價目須有明確轉換與精度規則。
- 同一筆使用的扣費順序必須固定，例如先使用即將到期的訂閱／贈送額度，再使用購買額度；退款按原始扣款來源還原。
- 初期預設週期額度不結轉、不允許負餘額、不自動收取超額費；開啟超額需有明確設定與客戶同意。
- 訂閱以帳務週期的明確時間邊界計算；初期方案變更與取消於下期生效，不做即時比例分攤。付款失敗不得授予新一期付費額度；已存在且仍有效的購買額度獨立處理。
- 金額採確定性精度與捨入規則；不得以浮點誤差累積帳務。實體表示由技術規格定義。
- 同時保留成本估算、成本確認狀態與客戶售價；成本修正不應默默重新向客戶追扣。
- 毛利報表需標明未包含的付款手續費、稅及基礎設施成本，不將未確認成本視為零。

驗收：相同用量可按不同開發者價目結算；成本與收入不混淆；到期、退款、訂閱續期與重複付款通知均不產生重複額度。

### FR-06：預留、結算與異常

正常流程：確認付款方及權限 → 依輸入、輸出上限及價目預留 → 執行 → 依用量結算 → 釋放差額。

- 無可計算上限的請求必須要求限制或拒絕，不能無限消耗後才檢查餘額。
- 客戶扣款預留與平台／部署者的 Provider 支出預算分別檢查；免費或低價服務不代表可以無限制產生成本。
- 每次 fallback 的上游支出都算入整個請求的成本預算；不能只限制最後成功的 Attempt。
- 同一冪等 key、同一請求內容只產生一個邏輯請求與客戶結算；同 key 不同內容必須拒絕。有效期間及重播串流方式由 API 規格定義。
- Provider 執行結果不明時保留 pending 狀態，透過對帳與受控處理收斂；不可一邊釋放全部預留一邊繼續無上限執行。
- 帳本採追加式調整，退款與更正不得刪除原始紀錄。

| 情況 | 客戶收費預設 | Provider 成本 |
| --- | --- | --- |
| 驗證拒絕／無候選／額度不足 | 不收費 | 未執行則無成本 |
| 首次失敗、fallback 成功 | 按成功結果契約收一次；失敗重試不額外轉嫁 | 記錄所有 Attempt |
| 全部失敗，未交付可用輸出 | 不收費並釋放預留；未知用量進入對帳 | 記錄已發生及待確認成本 |
| 串流已交付部分輸出後取消／中斷 | 按事前揭露的 per-token 規則結算可確認用量；缺資料時待對帳 | 記錄完整已知／待確認成本 |
| Per-task 未完成成功條件 | 預設不收任務費 | 各步驟成本仍保留 |

串流開始交付後不得透明換模型拼接內容。任務或工具可能產生外部副作用時，不能只靠 SuperRouter 的扣款冪等性保證外部動作恰好執行一次。

驗收：併發請求不超支可用額度；客戶重送、服務重啟與重複結算事件不重複扣款；任何長期 pending 都可被營運者查到並處理。

### FR-07：Subscriptions 與付款整合

- 將付款狀態、訂閱狀態與可用額度分離；付款通知必須驗證來源並可去重。
- 平台額度購買與「開發者向自己客戶收費」是不同交易關係，不共享一張混合帳本。
- 第一版支援一種付款整合與測試流程；自架可透過受權限控制的整合入口接收既有帳務系統事件。
- 人工調整必須附原因、操作者與 audit trail；一般 App key 不得自行鑄造 credits。
- 退款需處理已使用額度，退款範圍、拒付及稅務責任於商業上線前定案。

驗收：付款成功只授額一次；亂序／重複通知不造成訂閱狀態倒退或重複授額；付款整合中斷可重放與對帳。

### FR-08：管理與可觀測性

- 管理面涵蓋 Services、Models／Tiers、Providers、Routing、Pricing／Plans、Customers、Usage／Billing、Health、Logs 與存取權限。
- 顯示請求成功率、首 token 延遲、總延遲、fallback 比例、成本、收入、預估毛利與待對帳金額。
- 支援依 workspace、project、Service、customer、model、Provider、時間及 request ID 篩選與匯出。
- 每筆請求可檢視設定版本、候選排除原因、選路依據、Attempts、用量、成本及扣款狀態。
- 預設只記錄必要 metadata，不保存 prompt／completion 原文；內容記錄需明確啟用、設定保留期限及遮罩規則。
- 設定變更、價格發布、手動調額與 credentials 操作皆需稽核；Log 不顯示原始 secrets。
- 第一版至少提供餘額不足、Provider 故障與對帳異常的管理面提示；外部告警管道可後續擴充。

驗收：營運者能從一次客戶申訴追查到扣款與供應失敗原因；唯讀使用者無法改價或看到 secrets；不同租戶的查詢與匯出互相隔離。

### FR-09：套件、SDK、Skill 與範例 App

- 套件提供穩定公開介面與擴充點，Provider adapters 可獨立擴充；宿主 App 不須依賴管理 UI 才能初始化核心。
- 使用相同契約支援嵌入式整合與 standalone server；正式帳務必須有持久化，不以記憶體 demo 宣稱可正式收費。
- SDK 應覆蓋 Service 呼叫、串流、用量查詢及可識別錯誤；管理能力與一般呼叫權限分開。
- 提供版本相容範圍、升級與 migration 指南、環境變數範本及 secrets 排除規則。
- `skills/` 後續包含安裝／串接、建立 Service、設定 tier 與 pricing、診斷 routing／billing 的工作流程；skill 操作同一公開介面，不成為第二套業務邏輯。
- `examples/` 後續至少包含最小文字／串流 App、訂閱加 credits App，以及 self-host BYOK App；清楚區分 mock 與需要真實付費憑證的步驟。
- 範例 App 不內嵌真實 secrets，且說明客戶端與伺服器端的憑證邊界。

驗收：新使用者能依文件從乾淨環境完成範例，看到一次請求、選路、用量與結算；示範採用正式公開介面，不直接修改內部資料表。

### FR-10：Connect with SuperRouter（後續階段）

- 提供使用者授權 App 消耗個人平台額度的流程；登入與付款授權必須分開表達。
- 每次請求固定 Developer pays 或 User pays，不得在餘額不足時自動換付款方。
- 授權包含 App、Service、預算、期限與撤銷；預算須能抵擋併發超支。
- 撤銷後拒絕新請求；已預留的請求按既定取消與結算規則收斂。
- 使用者能查詢各 App 的授權與花費；App 不取得使用者的上游 credentials。
- 初期不包含開發者分潤、跨 self-host 錢包互通或任意轉帳；這些需獨立結算與商業規格。

## 7. 對外介面需求與後續 API 設計範圍

本 PRD 定義應有能力，尚不承諾具體 endpoint、JSON schema 或既有 API 的完全相容性。

| 介面面向 | 必須覆蓋的產品操作 |
| --- | --- |
| Serving | 發現可用 Service／模型、文字推論、串流、取消與結果狀態 |
| Configuration | Service 版本、模型群組、Provider connections、policy dry-run、價格與方案發布 |
| Customer billing | Customer、訂閱、entitlement、可用餘額、使用紀錄、退款／調整的受控操作 |
| Operations | Health、request trace、成本／收入、對帳異常與 audit 查詢 |
| Integration | 驗證過的付款事件、可重試的用量／帳務事件通知及去重識別 |
| Identity，後續 | App 註冊、使用者授權、預算限制與撤銷 |

共同要求：租戶與環境隔離、最小權限、冪等性、request ID、分頁、時間範圍、明確錯誤分類、API 版本與速率限制。錯誤需區分額度不足、無符合候選、上游失敗、限制條件衝突與暫時無法確認結算。

## 8. 非功能需求

| 面向 | 要求與驗證方式 |
| --- | --- |
| 帳務正確性 | 驗證併發預留、去重、重啟恢復與退款；測試情境中不得重複扣款或超過允許餘額 |
| 隔離與安全 | 對 API、背景工作、查詢及匯出驗證跨租戶拒絕；credentials 加密保存、可輪替且不可讀回原文 |
| 可靠性 | 管理面故障不應使已發布設定立即失效；帳務無法安全預留時拒絕新的付費請求，不放行無法記帳的消耗 |
| 可恢復性 | 驗證執行中重啟、事件重送、未知上游結果與 pending 回收；恢復流程需有操作文件 |
| 效能 | 基準測試分開報告路由／帳務額外延遲、首 token 延遲與 Provider 延遲，不將上游延遲歸為平台耗時 |
| 隱私 | 可配置內容記錄與保存期限；刪除個人資料和必要帳務保留的衝突需在上線前定義 |
| 可攜性 | Self-host 核心路徑離線於 Cloud 控制面仍可運作，僅需能連到其選用的 Provider 與本地依賴 |
| 可擴充性 | 加入 Provider 不修改既有 Service 契約；新模態以明確計量單位擴充 |

可用性 SLO、吞吐、延遲目標、備份 RPO／RTO 與預設保留期限，須依 P0 選定的部署規模及基準結果定案。這些是公開上線前的門檻，不是現有性能承諾。

## 9. 分階段範圍與退出條件

階段依賴為 P0 → P1 → P2 → P3 → P4；不以未估算的日期承諾交付。套件與 self-host 從 P1 開始驗證，不能到 Cloud 完成後才補做。

| 階段 | 交付內容 | 退出條件 |
| --- | --- | --- |
| P0：設計基線 | PRD、技術架構、資料模型、API 規格、套件邊界、測試／威脅模型與實作拆分 | 決定執行環境、第一批 Provider、儲存與帳務方案；規格能覆蓋正常與失敗旅程 |
| P1：核心垂直切片 | 可整合核心套件、standalone 路徑、兩個 Provider adapters、文字／串流、Service、specific／pool／tier、基本 routing、token／credits 預留結算、request trace、最小範例 | 一筆真實或明確標示的測試呼叫可端到端驗證成本與扣款；通過併發、fallback、斷線與重啟帳務情境；self-host BYOK 可執行 |
| P2：可營運 MVP | 多租戶權限、完整 routing 設定、固定週期訂閱、付款整合、Cloud 平台額度、管理介面、報表、對帳、SDK、skill 與三類範例 | Cloud 與 self-host 旅程皆可重現；Cloud 後端拒絕 BYOK；完成付款測試、資料隔離、備份還原及既定 SLO 驗證；商業上線決策已定案 |
| P3：任務與更多模態 | 非同步 Task、per-task 成功契約、重試／取消／事件通知、圖片／音訊等計量擴充 | 同一任務多次模型呼叫仍只按契約結算；副作用與重試限制有明確證據；每種模態通過獨立計量驗證 |
| P4：個人額度授權 | Connect with SuperRouter、User pays、App 授權與消費管理 | 授權、撤銷、過期、併發預算及付款方固定均驗證；不藉由隱式切換付款方完成請求 |

MVP 指 P2 完成；per-task 是完整產品的必要能力，但不列入第一個可營運 MVP。若上市條件要求一開始就有 per-task，須將 P3 的任務契約與結算提前，並重新估算範圍。

## 10. 端到端驗收場景

| ID | 場景 | 預期結果 |
| --- | --- | --- |
| AC-01 | 開發者發布 `chat/low` Service 並完成串流 | 回應、選路、用量、成本、售價與帳本可由同一 request ID 串聯 |
| AC-02 | 最便宜的 Provider 不符合資料地區限制 | 在評分前排除，所有 fallback 也遵守限制 |
| AC-03 | 主供應失敗，備援成功 | 記錄兩次成本；按成功契約只扣客戶一次 |
| AC-04 | Specific model 無可用 offering | 明確失敗，不替換成另一模型 |
| AC-05 | 多個請求同時消耗最後額度 | 預留在原子性保障下成功或拒絕，不超支 |
| AC-06 | 同冪等 key 重送或服務結算中重啟 | 不重複扣款，狀態可查詢並恢復 |
| AC-07 | 串流中斷、usage 缺失 | 不拼接另一模型；顯示 partial／pending 與收費處理狀態 |
| AC-08 | 價格與 tier 在請求進行中發布新版 | 該請求仍使用原始版本，後續請求才使用新版 |
| AC-09 | 訂閱續期通知重送、取消或付款失敗 | 不重複授額；依約定週期與狀態更新權利 |
| AC-10 | 嘗試跨租戶讀取帳務或用 App key 調額 | 拒絕並保留必要稽核資訊 |
| AC-11 | Cloud 提交上游 key；self-host 提交有效 key | Cloud 後端拒絕，self-host 可建立安全的 Connection |
| AC-12 | 全新環境依套件文件與範例操作 | 可重現 Service 呼叫與用量結算，沒有未揭露的內部依賴 |
| AC-13 | P3 任務呼叫多個模型但最後失敗 | 不收成功任務費，仍保留各次供應成本 |
| AC-14 | P4 使用者撤銷 App 授權或餘額不足 | 拒絕新消耗，不自動向開發者付款帳戶扣款 |

## 11. 成功指標

第一輪內部驗證先建立基準，未取得量測前不填入假定營收或效能數字。

- **啟用效率**：從乾淨環境到第一次可追溯成功請求所需時間；依 Cloud、套件、self-host 分開量測。
- **帳務可信度**：重複扣款、未授權超支與無法追溯結算的事件數；驗收測試的預期均為零。
- **路由效果**：相對固定 Provider 基準的成本、延遲、成功率及政策違反次數；品質須以指定任務評估，不能只看成本下降。
- **營運能力**：pending 結算數量／最長時間、Provider 故障定位時間與對帳差異。
- **開發者採用**：完成第一個 Service、持續使用及從範例進入正式整合的比例。
- **商業表現**：可確認的服務收入、Provider 成本與毛利；未知成本單獨列示。

## 12. 非目標與主要風險

初期不做通用 agent／工作流編排器、模型訓練、GPU 推論集群管理、任意錢包轉帳、開發者分潤市場、跨幣別結算或自動品質保證。Serving 初期是模型介面與服務交付，不包含代管模型權重的推論基礎設施。

| 風險 | 對產品的影響 | 處理方向 |
| --- | --- | --- |
| Provider 用量或成本資料不完整 | 毛利與客戶扣款可能失真 | 原始證據、估算標記、pending 與對帳 |
| 自動選模改變輸出品質 | 開發者無法維持產品契約 | 任務化 tier、固定版本、受控更新與評估 |
| 預留與真實成本差異 | 造成超支或平台吸收成本 | 輸出上限、總嘗試預算、保守預留與差異處理 |
| 嵌入套件與 Cloud 行為分歧 | 維護與遷移成本上升 | 同一核心與契約，範例共同驗收 |
| 任務／工具重試產生副作用 | 客戶業務動作重複 | 明確副作用邊界及外部冪等契約 |
| 平台轉售與付款責任未確認 | Cloud 商業上線受阻 | 上線前確認各 Provider 合約、商戶責任與退款政策；本 PRD 不作法律判定 |
